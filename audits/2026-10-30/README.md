## Findings and recommended order

1. **Load only the active project gallery.** `components/ProjectsSection/ProjectLaptopScene.js` iterates every project, fetches every gallery and loads additional textures with `Promise.all`. The Projects run transferred 16.1 MiB. Load the selected cover first, then its next slide; prefetch one adjacent project with a bounded queue. Limit texture resolution and dispose evicted textures. Compressed download bytes do not represent decoded GPU memory.
2. **Make the hero cheap to paint before starting effects.** Lighthouse identified the masked portrait-lighting element as the mobile LCP candidate. Its CSS mask requests `/ProfessionalMe2.png` (1,269,512 transferred bytes), bypassing responsive image optimization. Use an appropriately sized modern-format mask/image, discover the actual portrait early, and defer procedural scene creation until the readable hero is painted. Preserve the approved design. Lighthouse estimated about 1,095 KiB image savings in the first mobile run; this is an estimate, not a promised result.
3. **Reduce startup scene work.** Initial route JS is 204 kB according to Next's build summary, but lazy chunks and runtime scene creation add more work. First mobile run measured 17.2 s main-thread work and 9.8 s script execution under simulation. Large contributors included React and the R3F chunk; attribution does not prove those libraries alone are the root cause. Profile geometry creation, shader initialization, state commits and layout before choosing optimizations. Create inactive scene resources near entry, spread optional work across frames, and gate hidden image loading by section proximity. Several service images were fetched even on homepage entry.
4. **Add explicit Full / Balanced / Lite quality modes.** Existing offscreen pausing, demand rendering, DPR caps and reduced-motion branches are useful. Build on them with adaptive frame-time quality and a persistent user override. Lite should retain all information and links, use static illustrations, and simplify cinematic navigation. Do not infer performance solely from screen width or device age. Device-memory/data-saver signals can be optional hints, never sole requirements.
5. **Make rendering capability failure safe across the whole site.** Installed Three.js r168 requires WebGL 2 (confirmed in installed renderer source and official docs). Skills uses a half-float render target. Test WebGL 2 and required framebuffer capability, supply a lower-cost render target when possible, and render a complete static alternative on failure. Contact already has an error boundary and context-loss handling; apply equivalent protection consistently to hero, logo, journey and laptop. Mobile Skills still constructs desktop stars/rocks/routes/markers before hiding them: avoid unnecessary allocation.
6. **Fix measured accessibility failures.** Hero role paragraph uses prohibited `aria-label` on a plain `p`; use appropriate text semantics without continuously announcing typewriter glyphs. Contact email link triggered visible-label/accessibility-name mismatch; inspect duplicated animated label spans and provide a stable matching name. Contact GitHub/LinkedIn targets are about 12.5 px high and overlap/neighbor large asteroid hit regions. Increase target size (recommend 44 px), isolate decorative/game hit areas from links, then rerun. These are the automated failures; keyboard, screen reader, focus, zoom, contrast during animation and reduced-motion behavior still require manual checks.
7. **Stabilize direct section entry.** Investigate the Contact hash CLS 1, late section sizing and programmatic hash scrolling. Reserve the final runway dimensions and avoid repeated anchor correction as deferred scenes/images mount. Verify every hash with reload, back/forward navigation, rotation and resume-panel close.
8. **Review and upgrade vulnerable dependencies deliberately.** `npm audit --omit=dev` reported 10 packages: 1 critical, 6 high, 3 moderate. Next 13.5.6 is among the flagged direct packages; others include drei and PostCSS. The audit covers installed packages, not verified exploitability. Several advisories concern features this Pages Router app may not use. Review each advisory against deployment/configuration, choose patched compatible versions, and test the WebGL/React integration. Do not run force-fix blindly. Best Practices 100 does not certify dependency security.
9. **Remove avoidable network and rendering overhead.** Self-host/subset the two Montserrat weights currently loaded by CSS `@import`; avoid render-blocking font chains. First mobile audit estimated 970 ms render-blocking savings. Reduce filtered RGB image copies/scanlines and large blurs in Lite mode; only animate transform/opacity where the design allows. Scope these changes to measured bottlenecks. Source public assets total 43,093,334 bytes across 138 files; this is repository weight, not an initial page download.

## What remains to prove device coverage

- Run five sequential production audits per desktop/mobile profile and compare medians after each change; test the deployed HTTPS site with cold and warm caches, not only localhost.
- Record complete Hero → Journey → Projects → Skills → Services → Contributions → Contact sessions. Capture frame-time percentiles, long tasks, interaction responsiveness, GPU draw calls/triangles/textures and memory growth after three forward/back traversals. Navigation Lighthouse does not measure these comprehensively.
- Test actual low-end Android and an older supported iPhone, midrange devices, a modern phone, and an integrated-GPU laptop in Chrome/Edge/Firefox/Safari where available. Include sustained use/thermal load and battery-saving modes. Browser CPU emulation does not emulate old GPUs or mobile Safari.
- Check no-WebGL/context-loss behavior, reduced motion, keyboard-only and screen-reader operation, 200–400% zoom, slow/interrupted connections, touch/calendar/game gesture conflicts, resume focus restoration and all direct section anchors.
- Proposed acceptance goals: accessible content/links in every quality mode; no uncaught rendering failures; stable memory across repeated traversal; 60 fps target on capable devices and a usable 30 fps simplified experience on supported low-end hardware. Target LCP ≤2.5 s, CLS ≤0.1 and field INP ≤200 ms. Set budgets from real traces rather than promising every device can render the full scene.

## Brainstorm recommendation

Keep the full visual experience on capable hardware. Prioritize selective gallery loading, hero delivery and deferred scene initialization first, alongside the small semantic/target fixes. Introduce Balanced/Lite as a resilient product feature, then improve scores with repeatable measurements. Accessibility and Best Practices 100 are realistic automated targets; Performance 100 remains an aspiration until measured after these changes. A perfect score never proves universal device support.
